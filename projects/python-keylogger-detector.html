Python Keylogger & Detector

A paired offensive-behaviour and defensive-analysis lab: inspect a minimal Python keyboard-input logger, then evaluate a process-name heuristic intended to flag potentially suspicious processes.

01 — Objective & scope

This project puts a small keyboard-input logging proof of concept beside a simple defensive detector. The goal is not to claim complete keylogger detection; it is to understand what the sample does, what the detector actually observes, and where a name-based heuristic falls short.

The repository README describes two components: keylogger.py and detection/Keylogger_Detector.py. The analysis below is grounded in those source files. It does not claim that the detector has been validated against a representative malware dataset or that endpoint-product efficacy has been measured.

Safety boundary: use only in a disposable, isolated lab with synthetic typing and accounts you control. Do not collect credentials or other people's input. The diagrams on this page are explanatory illustrations, not screenshots or proof of a completed test run.

02 — Architecture & data flow

The keylogger and detector are separate scripts. That separation matters: the existence of both components does not mean the detector automatically detects the logger, nor that an alert proves malicious behaviour.

03 — Source analysis: keyboard-input logger

The source file is intentionally small. Its key behaviours can be traced directly:

  1. Register a global keyboard listener: Listener(on_press=log_keystroke) routes press events to a callback.
  2. Define a stop condition: if the event equals Key.esc, the callback returns False, which stops the listener.
  3. Normalise the event representation: it converts the key object to a string and removes single-quote characters.
  4. Append to a local file: the script opens keylog.txt in append mode and writes one event representation per line.
  5. Wait for listener completion: listener.join() blocks until the listener exits, after which the program prints a stopped message.

04 — Source analysis: process-name detector

The detector uses psutil.process_iter(['pid', 'name']) to enumerate processes and compares each lower-cased process name against three substrings: keylogger, logkeys, and xinput. If any substring appears, it prints the process name and PID. It catches NoSuchProcess, AccessDenied, and ZombieProcess exceptions so a changing process list does not abort the scan.

Its main value is as a first exercise in process enumeration and heuristic matching. It is transparent and easy to reason about, but the match itself is weak evidence: names can be changed, benign tools can match, and suspicious input monitoring can run inside a generically named Python process.

A stronger detector would combine several independent signals and provide context, instead of treating a process-name match as a verdict. For example, an analyst could correlate process ancestry, executable path, unusual input-monitoring behaviour, and repeated writes to a log-like file. These are proposed improvements, not features already implemented in this repository.

06 — Safe validation plan

  1. Static review first: inspect the two scripts and record their exact revision before any execution.
  2. Isolate the environment: use a disposable VM and synthetic, non-sensitive typing; avoid shared clipboard, real accounts, and production data.
  3. Validate the detector with benign fixtures: test the matching logic using controlled process-name examples or a unit-test mock rather than collecting real keystrokes.
  4. Record expected vs actual: save detector stdout, test setup, OS/Python versions and timestamps. Do not claim a pass without this evidence.
  5. Measure both errors: document false positives from legitimate names and false negatives when a test process has a generic name.
  6. Clean up: stop the test, remove synthetic logs and revert the disposable VM snapshot.
Evidence status: this page documents behaviour visible in source code and proposes a validation plan. It does not assert measured detection rates, successful EDR integration, or a completed live test.

07 — Limitations & lessons learned

  • Heuristic quality: process-name matching is brittle and can generate false positives or miss renamed/generic processes.
  • Limited telemetry: the detector does not inspect keyboard hooks, file writes, process ancestry, persistence, or network behaviour.
  • No correlation: the two scripts are separate; the detector does not establish that the logger caused a file change.
  • Platform dependence: keyboard-listener behaviour and permissions can vary by operating system and desktop environment.
  • Evidence discipline: source-code analysis supports a description of intended behaviour, while empirical claims require reproducible logs and test records.

The main lesson is that a useful defensive signal needs context. A process name can be a starting point for triage, but a reliable conclusion comes from correlated telemetry, repeatable validation and an explicit account of uncertainty.
