Wazuh SOC Lab

A virtual security operations lab built to connect endpoint and network telemetry, validate detections with controlled activity, and practise the investigation workflow behind a security alert.

01 — Objective: build a detection workflow, not just a dashboard

This lab connects endpoint telemetry, network inspection, firewall events and file-reputation context in one virtual environment. The engineering question is not simply whether Wazuh is running: it is whether an activity produces observable evidence, whether that evidence reaches the SIEM, and whether the resulting alert gives an analyst enough context to investigate.

Detection surface

Endpoint + network

Sysmon and Windows logging describe host behaviour; Suricata and pfSense add network and firewall perspectives. Wazuh is the place to review those different signal types together.

Analyst outcome

Evidence over assumptions

Controlled SSH brute-force activity is documented as detected. Other integrations provide additional visibility, but each signal still needs interpretation and scenario-specific validation.

02 — Architecture and telemetry flow

The repository describes a VMware-based lab with a Wazuh core server, a Windows monitoring host, a Kali test host, a pfSense gateway and a Suricata sensor. VirusTotal is used as an external reputation-enrichment layer for file hashes associated with monitored file changes.

03 — Investigation 01: SSH brute-force detection

The README documents a controlled SSH brute-force simulation with Hydra inside the virtual lab. Repeated authentication failures were detected by Wazuh and generated alerts for review. The useful analytical chain is to connect the repeated failures to the source, timing and authentication outcome, then decide whether the evidence supports escalation or a defensive response.

What an analyst should verify

  1. Group related failures by source and time window rather than treating each failure as a separate incident.
  2. Check whether the target account and authentication service are consistent across the event sequence.
  3. Look for a subsequent successful login or other relevant host activity before concluding that access was obtained.
  4. Record the alert rule and supporting event fields so the conclusion can be reproduced.
Interpretation boundary: repeated failures support a brute-force detection hypothesis. They do not, by themselves, prove a successful compromise. A successful login or follow-on activity needs separate evidence.

04 — Investigation 02: File Integrity Monitoring and reputation context

Wazuh FIM is configured to monitor selected Windows directories for file creation, modification and deletion. The repository also describes a VirusTotal integration that looks up hashes associated with monitored file changes. These functions answer different questions: FIM records that a file changed; reputation enrichment may add external context about the observed hash.

Signal A

File integrity event

Establishes that a monitored path changed. Review the path, action, timestamp and any available file metadata before deciding whether the change is suspicious.

Signal B

Hash reputation

Adds external context for the file hash. A benign or unknown reputation does not prove safety; a positive match still needs to be interpreted alongside the local event.

05 — Network visibility: Suricata + pfSense

Suricata is documented as the network inspection layer, using Npcap and custom rule sets; its alerts are forwarded into Wazuh. pfSense supplies firewall records, with custom decoders and rules for selected allowed, blocked and authentication-related activity. These sources can complement endpoint logs, but they are not interchangeable: an IDS alert describes what the sensor recognised, while a firewall record describes a policy or traffic event visible to the gateway.

Evidence sourceCan help answerDo not infer automatically
Suricata alertDid the sensor match traffic against a detection rule?That the endpoint was compromised or the traffic succeeded.
pfSense eventWhat connection or policy event did the firewall record?That an application-level action completed.
Sysmon / Windows logsWhat process or host activity was recorded?That all network traffic or all process behaviour was logged.

For an investigation, align timestamps and available source/destination fields, then look for agreement between independent sources. If only one layer has an event, treat it as a lead to investigate rather than a complete incident narrative.

06 — Validation approach

A useful detection test needs an expected result and evidence that the configured pipeline produced it. The repository describes a successful SSH brute-force detection exercise and documents the integrations. The following checklist captures the validation discipline I use when evaluating such a lab:

Validation stepEvidence to retainWhy it matters
Generate a controlled eventScenario, time, source and targetCreates a known starting point for the investigation.
Confirm collectionRelevant endpoint or sensor eventSeparates a logging gap from a detection-rule issue.
Inspect the alertRule ID, severity, timestamp and relevant fieldsShows what the SIEM actually concluded.
Correlate contextRelated events from other available sourcesReduces the risk of over-interpreting a single alert.
Record limitsMissing events, untested cases and assumptionsKeeps the claim proportional to the evidence.

07 — What the project demonstrates

The strongest part of this project is the integration mindset: endpoint, network, firewall and reputation data answer different questions, and an analyst has to combine them without overstating any one source.

Wazuh SIEMSysmon telemetrySuricata IDS/IPSpfSense loggingFile Integrity MonitoringThreat-intelligence enrichmentAlert triage

  • Integrating multiple defensive tools into one virtual monitoring workflow.
  • Relating controlled authentication activity to SIEM alerts.
  • Using FIM events and hash reputation as complementary evidence.
  • Distinguishing endpoint, network-sensor and firewall telemetry.
  • Documenting what was tested, what evidence exists and where the limits remain.

08 — Scope and limitations

  • This is a personal virtual lab, not a production SOC deployment.
  • Detection coverage depends on enabled logging, sensor placement, rules and the scenario tested.
  • A Suricata match, firewall record or file-reputation result is not proof of compromise by itself.
  • The public README describes Active Response as a defensive capability explored; the available material does not justify claiming that automatic blocking was fully validated end-to-end.
  • The diagrams in this page are explanatory summaries. The repository's original diagram and report remain the primary project artifacts.

All attack simulation described by the project is for the controlled virtual lab or other systems where explicit permission has been granted.
