Ravyn: JWT audience validation disabled

A source-code review found that Ravyn's built-in JWT decoding path disables audience validation. In a shared-trust, multi-service setup, this can let a valid token issued for one service be accepted by another service.

PythonJWT / PyJWTSource-code auditResponsible disclosure
Disclosure note. Ravyn v0.4.3 was released on 28 September 2026 and its official release notes describe the JWT audience/issuer validation fix and credit @sleepyguy396.

Summary

JSON Web Tokens (JWTs) can carry an aud claim, which identifies the service or recipient the token was issued for. If Service A and Service B trust the same signing key, audience validation helps prevent a token meant for Service B from being reused against Service A.

In the versions I inspected, ravyn.security.jwt.token.Token.decode() called PyJWT with options={"verify_aud": False}. That setting disables audience verification even if a caller also supplies an audience= argument. The built-in authentication backends did not pass an audience, and JWTConfig did not expose an audience setting.

The issue is not a signature forgery. The token still has to be validly signed by a key trusted by the target service. The flaw is that the framework does not check whether that otherwise-valid token was intended for the target audience.

Finding at a glance

  • Component: ravyn/security/jwt/token.py
  • Function: Token.decode()
  • Authentication paths reviewed: common, edgy, and mongoz built-in backends.
  • Affected versions reported: Ravyn v0.1.0 through v0.4.2; tested checkout 054ee1494ad8d662af531cafc5c74008514bf7b7. This is the affected range stated in my report; check the upstream advisory for the final official range.
  • Fixed in: Ravyn v0.4.3, according to the official release notes.
  • Root cause: audience verification is hard-disabled, and the built-in backend offers no audience configuration.
  • Classification considered: CWE-287 — Improper Authentication.

The inspected versions and commit describe the research environment, not a claim that every intermediate tag was individually tested.

Root cause in the code

The relevant call in Token.decode() passes a fixed options dictionary to PyJWT:

data = jwt.decode(
    jwt=token,
    key=key,
    algorithms=algorithms,
    options={"verify_aud": False},
    **kwargs,
)

The function accepts **kwargs, so audience="service-A" can be passed into it. However, the fixed verify_aud=False option tells PyJWT not to perform the audience check. In the built-in authentication path, the issue is more direct: CommonJWTAuthBackend.authenticate() calls Token.decode() with the signing key and algorithm only, without an audience or issuer.

The Edgy and MongoZ backends inherit that authentication method. After decoding, the backend looks up the user using token.sub. It does not compare aud against the service receiving the request.

Why the audience claim matters

Imagine two separate services that share a signing key but are intended to accept different tokens:

Service A expects: aud = "service-A"
Service B expects: aud = "service-B"

Token issued for B:
  sub = "1"
  aud = "service-B"

If that token is sent to Service A, a correct audience check should reject it because service-B does not match service-A. With the vulnerable code path, signature validation succeeds and the audience mismatch is ignored.

This only becomes a practical cross-service issue when services share a signing/trust configuration and are meant to be separated by audience. A single-service deployment with no other audience to confuse does not have this same attack path.

Validation: PyJWT control test

I first compared PyJWT's normal behavior with the call shape used by Ravyn. The test created a short-lived, locally signed token for service-B and attempted to decode it as a token for service-A.

# Normal PyJWT call
jwt.decode(
    token,
    key,
    algorithms=["HS256"],
    audience="service-A",
)
# Raises: InvalidAudienceError

# Same call shape as Ravyn
jwt.decode(
    token,
    key,
    algorithms=["HS256"],
    options={"verify_aud": False},
    audience="service-A",
)
# Accepted

This control isolated the behavior to the wrapper's options: PyJWT rejected the mismatched audience when audience verification was enabled, and accepted it when verify_aud was explicitly disabled.

End-to-end reproduction

I then tested the actual ravyn.contrib.auth.edgy JWT authentication flow rather than relying only on a direct call to Token.decode(). The local test created two ASGI applications with separate SQLite databases and the same HS256 signing key.

  • Service A: user ID 1 was alice-admin, a superuser.
  • Service B: user ID 1 was mallory, an ordinary user.
  • Each service received a token with its own audience claim.

The ID collision was deliberate: independent databases commonly assign the first row ID 1, and it made the identity-resolution effect easy to observe in a deterministic lab.

Control: Service A token -> Service A
HTTP 200 · authenticated_as=alice-admin

Control: Service B token -> Service B
HTTP 200 · authenticated_as=mallory

No token -> Service A
HTTP 401

Service B token -> Service A
Expected: reject audience mismatch
Actual: HTTP 200
         authenticated_as=alice-admin
         is_superuser=true
         data=A-INTERNAL-DATA

The target service accepted the Service B token, then resolved its sub value against Service A's own user table. Since that table mapped ID 1 to the superuser, the request ran as that account in the constructed demonstration.

Scope of this result: the identity collision was intentionally arranged for the proof of concept. It demonstrates the possible consequence of accepting a wrong-audience token; it does not mean every real deployment will map a token subject to a privileged account.

Prerequisites and limitations

A real deployment would need the following conditions for this finding to be exploitable:

  • The target uses Ravyn's built-in JWT authentication path, or equivalent code that does not independently validate the audience.
  • The services share a signing key or trusted verification configuration but are intended to accept different audiences.
  • The attacker already has a valid token issued under that shared trust configuration. No signing-key compromise or signature forgery was demonstrated or required.
  • The token's sub value resolves to an account in the target service. The resulting identity and privilege depend on the target's user-ID design.

Testing used HS256, PyJWT 2.14.0, Ravyn 0.4.2 at the tested local commit, and an Edgy-backed ASGI test setup with SQLite. The MongoZ backend was source-reviewed for the same inheritance pattern but was not separately tested end-to-end. Production ASGI servers and other signing algorithms were not independently tested.

Remediation

The proposed fix has two parts:

  1. In Token.decode(), only default verify_aud to False when the caller has not explicitly requested audience validation. If audience= is supplied, let PyJWT enforce it.
  2. Add optional audience and issuer settings to JWTConfig, then forward configured values from the built-in authentication backend to Token.decode().

This keeps existing audience-less usage compatible while allowing applications to explicitly enforce audience and issuer claims.

I tested the proposed change in a separate local copy of the repository. After the patch, mismatched and missing audiences were rejected when audience validation was requested; matching audiences continued to pass. Calls that did not request an audience retained their previous behavior, and issuer checks behaved as expected when explicitly requested.

Disclosure and upstream status

The finding was privately reported to the maintainer. The official Ravyn v0.4.3 release notes state that the release enforces JWT audience and issuer validation when expected values are passed to Token.decode() or configured for the built-in Edgy and Mongoz authentication backends. They also say that optional audience and issuer settings were added to JWTConfig, while deployments without an expected audience retain their existing behavior. The release notes credit @sleepyguy396 for reporting the issue.

The release notes link the report to upstream issue #739.
